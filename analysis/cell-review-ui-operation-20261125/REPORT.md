# Cell Review の操作の改善（2026-11-25）

Registration Explorer の「細胞対応レビュー（研究）」で、核の選択・拡大・左右比較・判定が別々の操作になっていました。これを、**モードを切り替えずに、左クリックで核を選ぶと拡大され、左右比較と判定にすぐ進める**操作に変えました。

UI と操作だけの変更で、計算・推定・保存形式は変えていません。

- 監査の結果（変更前の問題）は `audit.md` にあります。
- テストの結果は `test_results.md` にあります。

## 2. 操作（新しい方式）

| 操作 | 動作 |
|---|---|
| 左クリック | 最も近い H&E 核を選びます。その場で強調表示し、中央に移動します。最初の 1 回（全体表示に近いとき）は、周囲 60 µm が見える倍率まで拡大します。その後はユーザーが決めた倍率を保ちます。 |
| 候補の白い輪をクリック | 比較する候補を変えます。右の判定パネルのラジオボタンと、左右比較の右側の枠も切り替わります。 |
| Shift + クリック | 候補にない IF 核を、対応先として選べます（以前の「対応先の IF 核を選択」モードの代わり）。 |
| 左ドラッグ | 表示を移動します。押してから 5 CSS 画素を超えて動かした場合をドラッグとみなし、離しても核は選びません。 |
| ホイール | カーソルの位置を中心にズームします（変更前と同じ）。ズームした後も、クリックで選べます。 |
| 30 / 60 / 120 µm のボタン（ビューアの左側） | 選んだ核の周りを、その範囲で表示します。 |
| 「表示をリセット」（既存） | 全体表示に戻します。 |
| **1** / **2** / **3** / **4** | 対応確認（比較中の候補で）／ 未特定 ／ 非観測 ／ 判断不能 |
| **Enter** | 次の未レビュー核へ移ります（記録はしません）。 |
| **Ctrl+Z** / **Ctrl+Y**（Ctrl+Shift+Z も可） | 取り消し ／ やり直し。対象の核を表示します。 |
| **Esc** | 選択を解除します。 |

キーボードの扱いは次のとおりです。

- **キーが効く場所**：ビューアの中、ページ（判定パネルなど）、左右比較の中（ページへ転送します）。
- **キーが効かない場合**:
  - テキスト入力の欄（コメントや ID の欄）で入力しているとき。数字や Enter は文字として入ります。チェックボックスやラジオボタンにフォーカスがあるときは、キーが効きます。
  - 別のタブを表示しているとき。
- **判定ボタンにフォーカスがあるとき**：Enter で「次へ」だけを行い、そのボタンは押されません。
- **非観測（3）でコメントが空のとき**：保存せず、警告を出して、コメントの欄にフォーカスを移します。
- **記録するのは、明示的な判定操作だけ**です。核をクリックしただけでは何も記録しません。
- **「判定を記録したら次の未レビュー核へ進む」**（既定はオフ）：判定が実際に記録されたときだけ、次の核へ進みます。
  - 変更前は「対応を解除」などの判定以外の操作でも進んでいました。
  - 次の核へ進むときは、その核を中央に表示します。倍率は保ちます。

## 3. 画面の構成

- **左の列**：上に中央のビューア、その下に左右比較（30 / 60 / 120 µm）。
- **右の列（判定パネル）**：スクロールしても画面上部に固定されます（sticky）。上から次の順に並びます。
  - ID 入力
  - 選んだ核の ID、自動推定の状態、人のレビューの状態、現在の対応先
  - 候補の上位 5 件（ラジオボタン）
  - 比較中の IF 候補
  - コメント
  - 「判定を記録したら次の未レビュー核へ進む」
  - 判定ボタン（キー表示付き）
  - 解除、未レビューに戻す
  - 次へ、選択解除、取り消し、やり直し、保存
- **パネルの下にまとめたもの**（「選択核の詳細・細胞輪郭・補助タグ・その他の操作」）：
  - 候補の表
  - 細胞輪郭の判定
  - 補助タグ
  - 支持、候補の一覧から変更、任意の IF 核を対応先にする
- **左右比較**：
  - 左（H&E）は選んだ核を中心にします。
  - 右（IF）は比較中の候補を中心にします。候補が無いときは、Global 変換による予測位置を中心にします。
  - 現在の候補はマゼンタ、その他の候補は白い破線（#順位）、現在の対応先は緑、予測位置は黄色です。
  - 核輪郭、細胞輪郭、位置の同期は、変更前と同じです。

## 4. 実装（要点）

- **中央のビューア**：テンプレート（`viewer.py`）は変えていません。
  - テンプレートは `mode !== 'view'` のとき、ポインターのイベントを API に渡します。
  - Cell Review の API は常に `review` モードで動かし、その中でクリックとドラッグを区別します（`A.down` / `A.move` / `A.up`）。
  - 距離は CSS 画素で測ります。キャンバスとビューの変換は、デバイス画素（CSS 画素 × devicePixelRatio）です。
  - クリックの許容範囲は 12 CSS 画素です（変更前は 12 デバイス画素で、dpr 2 では半分になっていました）。
  - 古いモード（`pick_he` / `pick_if` / `view`）は API に残してあり、11-17 のテストがそのまま通ります。
- **再描画と再起動の抑制**：選択（`selected`）をシーンと別に送ります。
  - 選択だけが変わったときは、同じビューアのまま描き直します。画像の再読み込みや、左側のパネルの作り直しはしません。
  - シーンには `view_key` を入れました。判定などでシーンが変わってビューアを作り直しても、ズームとパンは元に戻ります。
  - 左側のパネルのレイヤーの表示・非表示と輪郭の設定も、元に戻ります。
- **Python との往復**：
  - ビューアのイベント（クリック・キー）は、Streamlit のコンポーネントの値として届きます。これを描画の前に読み、一度だけ処理します（nonce で判定）。そのため、クリック 1 回につき再実行は 1 回です（変更前は 2 回）。
  - 番号キーの判定は、JS が「表示中の核の index」と「比較中の候補」を付けて送ります。Python は、その核がパネルに表示中の核と一致したときだけ記録します。
  - 一致しない場合（選択の切り替えが Python に届く前に押した場合）は、その核を選ぶだけにします。記録はせず、もう一度押すよう案内します。
  - 記録は、ボタンと同じ `Review.apply()` を通ります。取り消し・やり直しは `Review.undo()` / `redo()` です。履歴・保存形式は変更前と同じです。
- **入力欄の扱い**：
  - ID の入力欄は `on_change` で 1 回だけ適用します。変更前は、文字が入っている間、毎回の再実行で選択を上書きしていました。
  - 別の核を選ぶと、コメントの欄を空にします。前の核のコメントが次の判定に付くのを防ぐためです。
- **左右比較**：ズーム（窓に対する倍率）、パン、表示の切り替えを sessionStorage に保存します。
  - 同じ核のまま再実行したとき：そのまま元に戻します。
  - 候補だけを変えたとき：右の枠だけを新しい候補へ移します（倍率は保ちます）。
  - 核を変えたとき：両方の枠を新しい中心へ移します（倍率は保ちます）。
  - 窓（30 / 60 / 120 µm）を変えたとき、または「選択核を中心に戻す」を押したとき：倍率を初期値に戻します。
- 画像の表示モード（RGB／核強調）は、核を変えても変わりません（実際のブラウザで確認）。

## 5. 未確認のこと・注意

- **実際のブラウザでの確認の範囲**：
  - 確認したのは、ヘッドレス Chromium（Linux、ソフトウェア描画）です。Firefox、Safari、Windows/macOS の Chrome、タッチパッド、ペンでは確認していません。
  - 確認には、Cell Review のタブだけを持つ最小のページ（`browser/review_app.py`）を使いました。Explorer の全体のページ（`page.py` のタブ構成）では、AppTest の既存のテストで表示を確認しただけです。
- **キーの転送**：左右比較の中で押したキーをページへ転送する処理は、静的な検査（HTML に含まれること）だけで確認しました。実際のブラウザでの押下は試していません。
- **人による操作感の評価**はしていません。開発サーバー 8511 を再起動したので、実際に操作して確認してください。
  - 確認してほしい点：連続レビューの速さ、60 µm への拡大が適切か、sticky パネルの見え方。
- **クリックの判定**：H&E 核と候補の輪が近いときは、クリック位置に近いほうを選びます。どちらを選んだかは、ビューアの左側の表示と判定パネルで確認できます。
- **ログインノードで確認できなかった理由**：ログインノード（gateway）では、Chromium が壊れた `/dev/nvidia0` を調べるため、起動に約 90 秒かかりました。また、ページの描画も 10 分以内に終わりませんでした。このため、ブラウザでの確認は Slurm の計算ノードで行いました（`browser/e2e.sbatch`）。
  - Chromium のソフトウェア描画は、`VK_ICD_FILENAMES` と `__EGL_VENDOR_LIBRARY_DIRS` で強制しています。
  - Playwright は別の環境（`~/envs/uitest`）に入れました。cell-rg には入れていません。
