# 監査: Cell Review の操作の流れ（変更前、HEAD 10b0fba、2026-11-25）

最新の `feature/gpu-slurm`（10b0fba）で、コードと実際の挙動を確認した結果です。

## 1. 中央のビューア（`cell_review_viewer.py`、テンプレートは `viewer.py`）

| # | 確認したこと | 影響 |
|---|---|---|
| A1 | クリック操作は `view` / `pick_he` / `pick_if` の 3 モードでした（左側のパネルで切り替え、既定は `pick_he`）。 | 核を選ぶ・動かす・IF核を選ぶたびにモードの切り替えが必要。 |
| A2 | `viewer.py` のテンプレートは、`API.mode !== 'view'` のとき pointerdown / move / up をすべて API に渡し、自分ではパンしません。旧 API の `A.down` と `A.move` は空でした。 | 選択モード中はドラッグしても動かない（ご指摘のとおり）。 |
| A3 | シーンに `view_key` がありませんでした。テンプレートの `saveView()` / `loadView()` は `S.view_key` があるときだけ働きます。 | Streamlit が再実行されてシーンが変わるたびに、ズームとパンが全体表示に戻る。 |
| A4 | 選択（`selected`）がシーンのハッシュに含まれていました。 | 核をクリックするたびにビューアが再起動する（キャンバスの作り直し、画像の再読み込み、左側のパネルの再構築）。A3 と合わせて、クリックのたびに全体表示へ戻る。 |
| A5 | クリックで値が Python へ送られて 1 回再実行され、そのあと `st.rerun()` でもう 1 回再実行されていました。 | 1 クリックにつき再実行が 2 回。 |
| A6 | クリックの許容範囲は `12 / v.k` でした。`v.k` はデバイス画素（CSS 画素 × devicePixelRatio）あたりなので、許容範囲は 12 デバイス画素です。 | 高解像度の画面（dpr 2）では許容範囲が 6 CSS 画素に半減する。 |
| A7 | 選択しても、その核へ移動・拡大する処理はありませんでした。 | 小さく表示された核を、手でズームして探す必要がある。 |
| A8 | 側のパネルのレイヤーの表示・非表示は、ビューアが再起動するたびに既定値に戻っていました。 | 判定のあとに、消したレイヤーがまた表示される。 |

## 4. 変更方針（変更してはいけないものを除く）

- `viewer.py` のテンプレートは変更しません。
  - テンプレートは、`mode !== 'view'` のときイベントを API に渡します。
  - Cell Review の API は常に `review` モードで動かし、その中でクリックとドラッグを区別します。
  - 区別は CSS 画素での移動距離で行います（`A.down` / `A.move` / `A.up`）。
- 選択はシーンと別に送り、同じビューアのまま描き直します。シーンには `view_key` を入れます。
- 左右比較は、表示の状態を sessionStorage に保存し、作り直しても元に戻します。
- 判定パネルは、ビューアの横の列に置き、スクロールしても見えるようにします（sticky）。
- キーで判定するときは、JS が「表示中の核 ID」を付けて Python に送ります。Python は、その核が表示中のときだけ、ボタンと同じ `Review.apply()` の経路で記録します。

変更しないもの（`baseline_manifest.json`、HEAD 10b0fba の sha256）:
- Graph/UOT/B2、核対応の推定、RBF、UOT conservative
- 細胞・核のセグメンテーション、画像の変形、Workflow C/D
- `viewer.py`、`cell_review.py`、`scene.py`、`page.py`

合計 65 ファイルです。

変更するのは次の 3 ファイルだけです。
- `cell_review_ui.py`
- `cell_review_viewer.py`
- `cell_compare_viewer.py`
