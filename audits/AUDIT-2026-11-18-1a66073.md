## 指摘1：未レビューの自動対応も「手動修正後」の変位場に残る

**重要度：高**

**事実：** `cell_review.py` の `Review._replay()` は自動対応を `decision="auto"` として初期化し、`pairs()` は判定状態を問わず対応先があるペアを返す。`reset` も自動対応へ戻す。一方、`review_annotations()` はこれらを `unreviewed` として、人の対応先には出力しない。`not_identified`、`absent`、`uncertain`、`exclude`、`unset` は対応先を外す。

`REPORT.md` §7 と実装前の `audit.md` §8 は、未特定・非観測・判断不能が REVIEWED のアンカーにならないと説明している。提示差分では、変位場のアンカー作成処理そのものは変更されていない。

**推測・影響：** 既存の REVIEWED 変位場が `review.pairs()` を使う場合、「手動修正後」という名称から全アンカーが人に確認されたと誤解され得る。提示された差分だけでは、その呼び出し経路全体や実際の出力を独立に確認できない。人のレビュー状態が Workflow C/D の自動採択を変更した証拠はない。

**改善案：** REVIEWED の入力に自動・未レビューの対応が含まれることを画面と出力に明記し、確認済みと未レビューのアンカー数を別記する。確認済みだけを使う選択肢が必要かは研究者が判断する。除外状態と `reset` を含むアンカー入力を回帰テストで確認する。

## 指摘2：「精度」の分母に未特定を含めるため、誤対応率としては解釈できない

**重要度：高**

**事実：** `cell_review.py` の `review_metrics()` は、algorithm matched のうち `confirmed_match`、`not_identified`、`absent` を分母とし、同じ top1 を `confirmed_match` したものだけを分子にする。`uncertain` と `released`、`unreviewed` は除外する。`REPORT.md` §3 では `not_identified` を「対応する核はあり得るが特定できない」と定義している。

**推測・影響：** `not_identified` は自動 top1 が誤りだと確定した状態ではないため、これを不一致として数える値は、確定可能なレビューだけで測った通常の精度とは異なる。レビュー対象の選び方や未特定の頻度によって値も変わる。`uncertain` と `released` の除外自体は判定不能・判定なしという定義に沿うが、除外件数と選択の偏りを併記しなければ代表性は判断できない。`non_match_rate` も未特定と非観測の合算であり、生物学的な非対応率とはいえない。

**改善案：** 現在の値を「決定的レビューに対する top1 確認割合」等、分母を反映した名称で扱う。未特定を別集計し、確定一致・確定不一致を区別できる定義、分母、除外件数、レビュー対象の抽出方法を事前に定める。人のレビュー基準であり生物学的正解ではないという注記は維持する。

## 指摘3：レビュー間一致は同一データの照合を保証していない

**重要度：中**

**事実：** `cell_review.py` の `review_agreement()` は両表を `source_index` のみで結合する。`sample_id`、`auto_id`、元の細胞 ID やセグメンテーション識別子の一致は検査しない。Cohen の κ は状態カテゴリについて計算し、対応先を含む一致は別の単純一致率として返す。周辺分布が完全に一つのカテゴリへ集中し、期待一致率が1の場合は κ を `None` とする。

**推測・影響：** 異なるサンプルや自動推定の表を誤って渡すと、同じ配列インデックスを持つ別の核が照合され、不適切な一致率が返るおそれがある。状態の κ は対応先の一致を保証せず、カテゴリの偏りや共通レビュー核の選択にも左右される。

**改善案：** 同一 `sample_id`・`auto_id`・核 ID・セグメンテーション識別子を検証し、不一致や重複を拒否する。共通レビュー核数、状態別件数、状態と対応先を含む一致率を κ と併記し、κ が状態のみの指標であることを明示する。

## 指摘4：輪郭の警告閾値は事後設定で、未検証

**重要度：中**

**事実：** `nuclear_contours.py` の `MAX_REL_OFFSET = 1.0` と、`load_contours()` の `inside_fraction < 0.5` はそれぞれ重心ずれと座標系不一致の警告に使われる。`REPORT.md` §7 は、開発ペアの実データで最大0.63を見た後に決め、検証していないと明記している。今回、これらを自動採択の Safety Gate に使った証拠はない。

**推測・影響：** 警告が出ないことは輪郭や座標系が正しい証明にはならず、開発ペアでの結果は独立検証にもならない。

**改善案：** 現行値を探索的な表示警告として扱い、採否基準に転用する前に、未使用ペアと座標系の取り違えなどの負例で、評価方法と基準を事前規定して検証する。

## 指摘5：セグメンテーション識別子と表示内容の対応には確認上の限界がある

**重要度：中**

**事実：** `nuclear_contours.py` の `identifier()` は輪郭ファイルのパス、SHA-256、結合キー、状態件数を返し、`cell_review.py` はレビューの `context` と注釈表にその識別子を保存できる。`load_contours()` のキャッシュキーはパス、更新時刻、倍率、中心点・ID 等に基づき、ファイル内容のハッシュ自体ではない。`section_contours()` は指定された読み込み例外を捕捉すると輪郭なしとして扱う。

`review_annotations.csv` の方向列は `HE` → `IF` に固定され、IF 起点の判定は未対応であることが `REPORT.md` §7 に明記されている。schema `/1` と `/2` の読み込みは `Review.from_json()` で許可されている。auto ファイルの SHA-256 保護は報告・テスト結果に記載されるが、保護処理の全体は提示されていない。

**推測・影響：** 内容が変わっても更新時刻などのキャッシュキーが同じ特殊な場合、表示と記録される識別子が古いキャッシュに依存し得る。また、輪郭なしが本来の点群専用データなのか、読み込み失敗なのかを後から区別しにくい可能性がある。方向列があるだけで双方向レビューが可能と解釈してはならない。

**改善案：** レビュー開始・再開・出力時に実ファイルの識別子と保存済み context の一致を確認し、不一致や読み込み失敗を明示する。中心点入力を含む識別子も必要に応じて記録する。表の利用時は H&E 起点のみという制約を維持する。

## 指摘6：テストと変更なし確認は有用だが、回帰全体やブラウザ操作の証明ではない

**事実：** `test_results.md` は、GPU を要求しなかった初回実行で GPU 一致テスト2件が失敗し、GPU 付き再実行で通過したと記録している。UI テスト1件の失敗後には CSV ボタンを追加し、テスト手順も変更している。最終の Slurm 実行では Node 不在のため各テスト群に skip があり、今回の Node テストはゲートウェイで通過したと記載される。ログは Git に含まれない。

**推測・影響：** GPU 条件を訂正して再実行し、失敗と訂正を残した扱いは妥当。ただし UI のテスト手順変更が元の期待を保っているかは、提示抜粋だけでは判断できない。41ファイルが同一でも、変更された UI・研究コードとの相互作用や実行時の回帰まで否定できない。

**改善案：** 最終コードに対する実行条件とログを追跡可能に保ち、UI テストの変更前後の期待を確認する。実ブラウザでクリック、ズーム、同期、画像・輪郭の対応、保存・出力を確認し、結果と環境を記録する。Node による確認とブラウザ確認は区別して報告する。
