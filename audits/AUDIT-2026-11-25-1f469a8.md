## 指摘事項

### 高：ID 入力の変更時に、もう一方の古い ID も再適用される

- **根拠**：`src/registration_explorer/cell_review_ui.py` の `_type_select()`、`_nucleus_panel()`。両 ID 欄は同じ `on_change` を使い、コールバックは変更された欄にかかわらず H&E と IF の両方の入力値を処理する。
- **事実**：H&E ID 欄に値が残っている状態でクリックや次核への移動により別の核を選び、その後 IF ID 欄を編集すると、古い H&E ID が先に再選択される。逆に、IF ID 欄に値が残ったまま H&E ID を変更すると、その古い IF ID が新しい H&E 核の比較候補として設定される。
- **推測・影響**：表示を見落として判定すると、意図しない H&E 核または IF 候補にレビューを記録し得る。提示テストには、この入力順序を確認するケースが見当たらない。
- **改善案**：変更された欄だけを適用する別々のコールバックにし、核変更時の IF 入力値の扱いを明示する。H&E ID 入力→クリックで別核→IF ID 入力、および IF ID 入力→H&E ID 変更の両順序で、表示と保存先を検証する。

### 中：候補選択の反映途中に、キーイベントの古い候補が優先され得る

- **根拠**：`cell_review_ui.py` の `_handle_event()`、`_cmp_state()`、`_nucleus_panel()`。`cell_review_viewer.py` の `A.key()`。
- **事実**：番号キーはビューア側の `he` と `active` を送る。Python は H&E 核の一致を確認するが、一致した場合はイベントの `active` を比較候補のセッション状態に設定する。候補の版や、キー押下時のパネル表示との一致は照合しない。
- **推測・影響**：ラジオボタンによる候補切替とビューアへの再描画の間に `1` を押すなど、両者が一時的にずれた場合、古い候補が確認される可能性がある。提示証拠だけでは実ブラウザでの再現や発生頻度は確認できない。核の不一致を拒否する既存の保護は、この同一核内の候補のずれを検出しない。
- **改善案**：候補を含む表示状態の版をイベントに付け、不一致時は判定せず再確認を求める。候補の切替直後に `1` を押す遅延・連続操作を実ブラウザで検証する。

### 中：近接した核と候補の輪は、操作者の意図と異なる対象が選ばれ得る

- **根拠**：`cell_review_viewer.py` の `A.pickAt()`、`A.click()`。
- **事実**：12 CSS 画素以内の H&E 核と、選択中の核の IF 候補を中心点までの距離で比較し、同距離では候補を優先する。輪の描画形状そのものはヒット判定に使わない。クリック自体は判定を記録しない。
- **推測・影響**：密集領域や核と候補が重なる場所では、意図した核ではなく既存核の候補が選ばれ、そのまま `1` を押すと意図しない対応の確認につながり得る。報告書も近い方を選ぶ仕様を明記しているが、提示テストは曖昧な重なりや同距離を十分に示していない。
- **改善案**：曖昧な距離では選択を保留して対象を明示する、または候補と H&E 核を明確に選び分ける操作を設ける。重なり・同距離・密集領域で、選択表示と記録対象を合わせて検証する。

### 中：左右比較の同期が有効な場合、候補中心の表示が上書きされる

- **根拠**：`cell_compare_viewer.py` の `restore()`、`syncFrom()` と初期化処理。
- **事実**：同期が有効な場合、候補または核が変わると `restore()` の後に `syncFrom(0)` が呼ばれ、右枠は左枠の Global Affine 変換位置を中心にする。これは報告書の「候補だけを変えたとき右の枠だけを新しい候補へ移す」という説明に条件が必要な挙動である。
- **推測・影響**：比較中の候補が右枠の中心から外れ、倍率や距離によっては見えにくくなる可能性がある。判定先自体が変わるという証拠はない。
- **改善案**：同期有効時の中心の優先関係を UI と報告書に明記し、候補切替・核切替・中心へ戻す操作を同期オン／オフで検証する。
