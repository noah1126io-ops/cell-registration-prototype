## 指摘1【高】現在のレビューと異なる変位場・画像を、同一結果として出力できる

**根拠：** `cell_review_ui.py` の `_deformation_section`、`_image_section`、`_review_hash`、`cell_review.py` の `export_bundle`。

**事実：**

- レビュー変更後、`used != cur_hash` でも警告を出して以前の変位場を使用し、画像生成・出力を継続できる。
- `export_bundle` は現在の `rv` から対応ペア・履歴を保存する一方、渡された変位場がそのレビューから計算されたか確認しない。
- 画像キャッシュには実際に使用した変位場の識別子がない。保存するハッシュは画像生成時の現在のレビューから作られるため、古い変位場で作った画像に現在のレビューハッシュが付く経路がある。
- 変位場再計算後も以前の画像が残り、画像への核の重ね描きには現在の `fields[m]` が使われる。衝突除外設定の変更も画像キャッシュの照合対象になっていない。

**推測される影響：** CSV・レビュー履歴・変位場・PNGが互いに異なる計算状態を表し、手動修正の効果や画像と点の一致を誤って評価しうる。

**改善案：** 計算時のレビュー、衝突除外設定、変位場を一つのスナップショットとして識別する。画像もその識別子に結び付け、状態不一致時は生成・出力を停止する。過去結果を出力する場合は、その計算に使ったレビューも保存する。

## 指摘2【中】保存結果と現在の入力核集合の同一性を確認していない

**根拠：** `cell_review.py` の `compute_auto`、`load_auto`、`compute_fields`、`Review._check_ids`、`export_bundle`、`cell_review_ui.py` の `render`。

**事実：**

- 自動推定には座標ハッシュと核数が記録されるが、読み込み後に現在の座標・IDとの照合は行われない。
- 保存された対応は全体インデックスで管理され、現在読み込んだ核配列に直接適用される。
- ID配列自体のハッシュは記録されない。
- レビューのID検査は配列全体の範囲確認であり、自動推定のROI内のHE核であるかは確認しない。通常のUI選択ではROIを制限しているが、計算側には同じ制約がない。

**推測される影響：** 同一サンプルの核ファイルの並びや内容を更新すると、保存レビューが別の核に適用されても検出できない可能性がある。

**改善案：** 座標とIDの順序を含む入力識別情報を保存し、読み込み・再計算・出力前に照合する。レビュー操作の対象HE核が `auto.he_idx` に含まれることも計算側で検証する。

## 指摘3【中】自動推定・レビューの整合性検証が限定的である

**根拠：** `cell_review.py` の `save_auto`、`load_auto`、`Review.start`、`Review.from_json`、`load_review`。

**事実：**

- `files_sha256` はCSVとNPZについて記録されるが、`auto_meta.json` 自身は対象外である。
- `load_auto` はメタデータ中に列挙されたハッシュだけを検証する。必須一覧の存在を要求せず、一覧が欠落すれば照合されない。
- Global変換、ROIなどのメタデータ変更は、この仕組みでは検出されない。
- レビューの `auto_sha` は保存されるが、読み込み後に選択中の自動推定と比較されない。レビュー内に複製された `auto_pairs` の一致も確認されない。

**推測される影響：** ファイル破損や取り違えにより、元の推定・変換・レビューの組合せが変わっても処理が進む可能性がある。「改ざんをsha256で検出」は、列挙されたデータファイルの変更検出に限定して解釈すべきである。

**改善案：** メタデータを含む成果物全体の整合性を検証し、必須ファイル・ハッシュ一覧を要求する。レビューを開く際に `auto_id`、`auto_sha`、核数、元の対応を照合する。

## 指摘4【中】TAPERは追加の変換であり、「厳しくするだけのゲート」という説明は成立しない

**根拠：** `cell_review.py` の `FieldResult.forward_displacement`、`taper_gradient_max`、`compute_fields`、`REPORT.md` §7。

**事実：**

- 被覆率0.20の条件はAUTO／REVIEWEDを棄却する追加ゲートである。
- TAPERは棄却条件ではなく、格子外に境界変位を延長して減衰させる写像である。
- 提示コードには、減衰帯を含む写像全体のJacobian等を再監査する処理や、`taper_gradient_max` による棄却条件がない。
- `taper_gradient_max` は境界変位の最大ノルムを50µmで割った値であり、境界に沿う変位変化を含む全勾配の上限ではない。
- smokeでの値は約0.0466〜0.0760であるが、将来の入力にも「最大0.08」を保証する制約はない。
- Dには、今回追加された被覆率チェックの分岐がない。

**推測される影響：** 格子内の監査結果を、減衰帯を含む実際の写像全体の安全性と誤読するおそれがある。今回の実データで減衰帯に折り返しが発生した証拠はない。

**改善案：** 被覆率ゲートと境界処理を別々に説明し、適用方式を明記する。減衰帯を含む写像を監査し、勾配指標の名称・定義と「0.08」の適用範囲を修正する。値の根拠が未確立であるとの留保は維持する。

## 指摘5【中】逆写像の非有限値が「不収束」として数えられない

**根拠：** `cell_review.py` の `invert_field`、`sample_pyramid`、`warp_he_roi`。

**事実：**

- 逆写像の結果がNaN／Infなら、`sample_pyramid` はその画素を `valid=False` とする。
- 不収束画素数は `~ok & valid` で数えるため、その画素は除外される。
- `APPLIED` 判定には有限値チェックや有効画素の最低条件がない。

**推測される影響：** 数値的失敗が画像範囲外と同様に扱われ、`APPLIED` と表示される可能性がある。ただし、提示されたsmoke結果はいずれも有限の残差を示しており、この障害の実発生は確認されない。

**改善案：** 逆写像の非有限値を独立した失敗として扱う。通常の画像範囲外と数値的失敗を分け、有効画素ゼロの場合も適用成功としない。

## 指摘7【低】研究タブの実行時にsrc配下を書き換える

**根拠：** `cell_review_viewer.py` の `interactive`、`cell_review.py` の `git_info`。

**事実：** コンポーネント初期化時に `src/.../interactive_cell_review/index.html` を生成・更新する。追跡済みファイルとの差分が発生すれば、`git_info` のdirty記録にも影響する。

**推測される影響：** 読み取り専用配置での起動失敗や、UI起動による作業ツリー変更が起こりうる。今回実際にdirtyになった証拠はない。

## 指摘8【低】画面の「P(match)」表記が、スコア定義より強く読める

**根拠：** `cell_review.py` の `compute_auto`、`cell_review_ui.py` の `_nucleus_panel`。

**事実：** `score_definitions` は、B2出力が実データで較正されず、同一細胞の確率ではないと明記している。一方、常時表示される採用理由には `P(match)=...` が使われ、留保は別の展開欄にある。

**推測される影響：** 採用理由だけを読む利用者が、実データでの同一細胞確率と受け取る可能性がある。

**改善案：** 採用理由も「B2スコア」とし、「実データ未較正・同一細胞確率ではない」を近接表示する。UOTの `mass_share` の定義自体は適切である。
